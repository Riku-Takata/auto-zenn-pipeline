# 自己進化型・技術ブログ自動生成システム（Auto-Zenn-Pipeline）基本設計書

## 1. システム概要 (System Overview)

### 1.1 背景と目的
生成AIの普及により、単なる「How-to（使い方）」や「エラー解決」の技術記事の価値は低下している。現在、エンジニアのポートフォリオや技術ブログに求められているのは、**「なぜそのアーキテクチャ・技術を選定したのか（Why）」「どのようなトレードオフを考慮し、AIをどう制御（Steering）して実装に落とし込んだか」**という思考プロセスと意思決定の記録である。

本システムは、日々のAIとの開発・壁打ちログから上記の思考プロセスを抽出し、Zenn記事のドラフトを自動生成する。さらに、**「生成されたドラフトに対する人間（著者）の修正差分（Git Diff）やレビューコメント」をフィードバックとして収集・言語化し、システムプロンプトを自己進化させる（Human-in-the-Loop）**ことで、最終的に著者の思考・文体を完全に模倣した自律的な記事生成パイプラインを構築することを目的とする。

### 1.2 システムのコアバリュー
1. **ADR（Architecture Decision Record）ベースの記事生成:** 単なる要約ではなく、技術選定の背景・代替案との比較・AIの軌道修正ログに焦点を当てた記事を生成する。
2. **GitHub完結のフィードバックUI:** 専用UIを作らず、GitHub Pull Request（PR）上のコードレビューと修正コミットをそのまま「人間の判断ログ」として収集する。
3. **メタプロンプトによる自己進化（LLMOps）:** 初稿と最終稿の差分（Diff）から「著者の暗黙知・こだわり」を抽出し、ガイドラインを自動更新することで、回を重ねるごとに手直し不要な精度へ収束させる。

## 2. システムアーキテクチャ (System Architecture)

本システムはGitHubリポジトリを中心に据え、GitHub ActionsとClaude APIを用いたイベント駆動型のパイプラインとして構築する。

### 2.1 全体ワークフロー図

```mermaid
graph TD
    subgraph 1. 開発・ログ収集フェーズ
        A[ローカル開発 / AI壁打ち] -->|自作ハーネス| B(GitHub: 開発ログ保存)
        A -->|コードPush| C(GitHub: ソースコード / Commit履歴)
    end

    subgraph 2. 記事ドラフト生成フェーズ (Generator)
        B & C -->|Trigger: ログ追加 or 手動実行| D[GitHub Actions: 記事生成ワークフロー]
        G[(ルールDB: writing_guidelines.md)] -->|参照| D
        D -->|Claude API: ADR構造化 & 執筆| E[Zenn Markdown 初稿生成]
        E -->|自動作成| F(GitHub: 記事Draft PR)
    end

    subgraph 3. 人間による評価・介入フェーズ (Human-in-the-Loop)
        F -->|レビューコメント / 直接編集コミット| H[著者によるブラッシュアップ]
        H -->|承認 & マージ| I(PR Merged)
    end

    subgraph 4. 公開 & 自己進化フェーズ (Evaluator / Optimizer)
        I -->|Zenn GitHub連携| J((Zenn & ポートフォリオへ自動公開))
        I -->|Trigger: PR Merge| K[GitHub Actions: 学習ワークフロー]
        K -->|初稿と最終稿のGit Diff & コメント抽出| L[Claude API: メタ評価・ルール抽出]
        L -->|暗黙知の言語化・PR作成または直接更新| G
    end
```

## 3. ディレクトリ構成案 (Repository Structure)

ZennのGitHub連携仕様に準拠しつつ、ログ管理とプロンプトの自己進化を組み込んだモノレポ（または専用リポジトリ）構成とする。

```text
zenn-auto-blog-repo/
├── .github/
│   └── workflows/
│       ├── 01_generate_draft.yml      # ログから記事ドラフトPRを生成するAction
│       └── 02_learn_from_feedback.yml # PRマージ時にDiffからルールを学習するAction
├── articles/                          # Zenn公開用記事ディレクトリ (Zenn CLI標準)
│   └── [slug].md
├── raw_logs/                          # 自作ハーネスからPushされる開発・会話ログ
│   └── YYYY-MM-DD_session_id/
│       ├── chat_history.json          # AIとの会話生ログ
│       └── git_context.json           # 関連するコミットログやPR差分など
├── prompts/                           # AIの頭脳となるプロンプト・知識ベース
│   ├── system_generator.md            # 記事生成用ベースプロンプト
│   ├── system_evaluator.md            # Diff解析・ルール抽出用メタプロンプト
│   ├── writing_guidelines.md          # 【自動更新】学習された執筆ルール・判断基準
│   └── few_shot_examples/             # 【自動更新】過去の良質な修正前後ペア（Before/After）
└── scripts/
    ├── generate_article.ts            # 記事生成スクリプト
    └── extract_feedback.ts            # Diff抽出・ガイドライン更新スクリプト
```

## 4. 機能要件と処理フロー (Functional Requirements)

### 4.1 開発ログ収集モジュール（既存ハーネス連携）
* **入力:** 開発中のClaudeとの壁打ちログ、および対象プロダクトのGitコミット履歴/Diff。
* **処理:** セッション単位で構造化データ（JSONまたはMarkdown）として `raw_logs/` ディレクトリへPushする。

### 4.2 記事ドラフト生成モジュール（Generator）
* **トリガー:** `raw_logs/` へのファイル追加、またはGitHub Actionsの `workflow_dispatch`（手動実行）。
* **処理ステップ:**
  1. **コンテキスト読み込み:** 対象の `raw_logs` と、現在の `prompts/writing_guidelines.md` を読み込む。
  2. **ADR抽出（思考の骨組み作成）:** 会話ログから以下の4要素を抽出する。
     * `Context`: 解決したかった課題、前提条件、制約。
     * `Options`: 検討した技術や設計の選択肢（AIが提案して却下したものを含む）。
     * `Decision & Why`: 最終的に選んだアプローチとその理由（トレードオフの判断）。
     * `AI Steering`: AIの初期回答のどこが不十分で、人間がどうプロンプトで軌道修正・深掘りさせたか。
  3. **記事執筆:** 抽出したADRと `writing_guidelines.md` のルールに従い、Zenn形式のMarkdownファイルを `articles/` に生成する。
  4. **PR作成:** 生成した記事を含むブランチを切り、Pull Requestを自動作成する。この際、**初稿のCommit Hashを記録**しておく（後のDiff抽出用）。

### 4.3 フィードバック収集・介入モジュール（Human-in-the-Loop）
* **インターフェース:** GitHub Pull Request画面。
* **人間のアクション:**
  * **直接編集:** 文章のトーン変更、一次情報（実際の計測値やハマった所感）の追記、不要な解説の削除を行い、PRブランチへCommit & Pushする。
  * **レビューコメント:** 「こういう基本的な使い方は省いていい」「次回からは〇〇の観点も入れて」といったメタな指示をPRコメント（またはインラインコメント）として残す。
* **完了条件:** 記事の品質が担保できた段階で、人間がPRを `main` ブランチへマージする（これによりZennへ自動デプロイされる）。

### 4.4 自己進化・ルール抽出モジュール（Evaluator / Optimizer）
* **トリガー:** 記事生成PRの `merged` イベント。
* **処理ステップ:**
  1. **データ取得:** GitHub API（またはGitコマンド）を用い、以下の3つを取得する。
     * AIが作成した初稿（Initial Commit時点のファイル内容）
     * 人間がマージした最終稿（Merge Commit時点のファイル内容）
     * PR上に残された人間のレビューコメント一覧
  2. **Diff解析と暗黙知の言語化:** `system_evaluator.md` プロンプトを用い、Claude APIに「初稿」「最終稿（Diff）」「コメント」を入力。**「なぜ著者はこの修正を行ったのか？」を分析させ、汎用的なルールに変換**させる。
  3. **知識ベースの構造化更新:** 抽出されたルールを以下の3レイヤーに分類し、`prompts/writing_guidelines.md` を更新する（重複ルールの統合や矛盾の解消も同時に行う）。
     * **Layer 1: 企画・構成（Structure）** - 章立て、結論ファースト、読者ターゲットの前提知識レベルなど。
     * **Layer 2: 技術的深掘り（Tech Depth）** - 省略すべき基礎知識、強調すべきアーキテクチャの観点、コードブロックの粒度など。
     * **Layer 3: 文体・トーン（Style & Tone）** - 語尾、禁止ワード（AI特有の冗長な表現など）、見出しの付け方、箇条書きの頻度など。

## 5. プロンプト＆データ設計 (Prompt & Data Design)

### 5.1 自己進化するガイドライン (`writing_guidelines.md`) のスキーマイメージ
AIが迷わず参照できるよう、Markdownの構造を固定してルールを蓄積する。

```markdown
# 執筆ガイドライン（自動更新ログ）

## 1. 企画・構成ルール (Structure)
- [Rule-S01] 冒頭の「はじめに」で、この記事で解決するアーキテクチャ上の課題と結論を3行以内で提示すること。
- [Rule-S02] ツールのインストール手順や公式ドキュメントを見ればわかる初期設定は一切書かないこと。

## 2. 技術的深掘りルール (Tech Depth)
- [Rule-T01] ライブラリを選定した際は、必ず「比較対象となった代替技術」を最低1つ挙げ、なぜそちらを選ばなかったのか（トレードオフ）を明記すること。
- [Rule-T02] AIとの壁打ちで「AIの最初の提案を却下した場面」があれば、その理由を「アンチパターン」として1セクション設けて解説すること。

## 3. 文体・トーン＆マナー (Style & Tone)
- [Rule-M01] 文末は「だ・である」調ではなく、落ち着いた「です・ます」調を基本とするが、「〜と言えるでしょう」「いかがでしたか？」といったAI特有の表現は厳禁とする。
- [Rule-M02] 1つの段落は最大4行までとし、論理の転換点では積極的に箇条書きまたはMermaid図を使用すること。
```

### 5.2 メタ評価器（Evaluator）のプロンプト設計指針
Diffからルールを抽出する際のシステムプロンプトには、以下の制約を設ける。
* **過学習（Overfitting）の防止:** 「『React』を『Next.js』に書き換えた」という事実そのままではなく、「フレームワークの名称は実際の実行環境に厳密に合わせる」あるいは「文脈に応じた抽象度でルール化する」よう指示する。
* **ルールの新陳代謝:** ルールが無尽蔵に増えてコンテキストを圧迫するのを防ぐため、既存の `writing_guidelines.md` を読み込ませ、「既存ルールと統合できるものは統合し、常に全体で30項目以内に要約・再編成して出力せよ」と制約をかける。

## 6. 段階的実装ロードマップ (Implementation Roadmap)

いきなり全自動の学習ループを作るとデバッグが困難になるため、以下の3フェーズで段階的に構築する。

### Phase 1: MVP（ログからのADR記事ドラフト生成）
* **目標:** 自作ハーネスのログから、Zenn形式のMarkdownを生成し、GitHub PRを立てる部分までを実装する。
* **タスク:**
  * `01_generate_draft.yml` と生成スクリプトの作成。
  * 初期のベースプロンプト（ADR抽出ロジック）の調整。
  * まずは手動で3〜5本ほど記事を修正・公開し、どんな修正が発生しやすいかの傾向を人間が掴む。

### Phase 2: Diff抽出とフィードバック学習の半自動化
* **目標:** PRマージ時にDiffとコメントを解析し、ルール抽出を行うスクリプトを実装する。
* **タスク:**
  * `02_learn_from_feedback.yml` の作成。
  * **安全装置:** 最初は `writing_guidelines.md` を直接上書きせず、「ガイドライン更新用のPR」をAIに立てさせ、人間が抽出されたルールをレビューしてマージする運用にする。

### Phase 3: 完全自律化とポートフォリオ連携
* **目標:** ルール抽出の精度が安定したらガイドラインの更新を自動化し、ポートフォリオサイトへの連携を完了させる。
* **タスク:**
  * Few-shot（修正前後の具体例ペア）の動的挿入ロジックの追加（より文体の再現度を高めるため）。
  * ZennのRSSフィードまたはAPIをポートフォリオサイトに接続し、記事公開と同時にポートフォリオの「技術ブログ・思考ログ」セクションが自動更新されるようにする。
  * **最終仕上げ:** 「この自己進化型ブログ生成システム自体の設計と運用結果」を、このシステムを使ってZenn記事として出力し、ポートフォリオの看板記事にする。
